# Ассистент сервисной службы на Graph RAG

Отчёт по проекту дисциплины «ИИ-мышление». Университет ИТМО. 14 ноября 2026 года.

**Участники:** Дьячков Андрей Дмитриевич; Дзюба Данила Тарасович; Сафонова Ольга Данииловна.

## 1. Задача

Диспетчеру сервисной службы нужно определить неисправный узел по модели оборудования и коду ошибки, подобрать действующий артикул, проверить склад и цену, затем подготовить заказ. Сведения распределены между руководствами, бюллетенями о заменах, отчётами инженеров и ERP. По [требованиям задания](docs/requirements.md) ассистент должен связать их и указать источники ответа.

На вопрос «Какую деталь заказать при ошибке E-17 на AR-210?» обычный RAG ответил P-1042. Это исходное пусковое реле; бюллетень о замене на P-1042B не попал в найденные фрагменты. Для таких задач близости текста к вопросу недостаточно: требуется проследить связи между моделью, узлом и ревизиями детали.

## 2. Решение

### 2.1. Подготовка базы знаний

Корпус содержит 80 документов: 12 руководств, 10 бюллетеней, 18 регламентов и 40 отчётов о ремонте. Подготовка данных выполняется перед ответами:

```text
Документы -> 92 фрагмента -> сущности и связи -> граф -> сообщества -> сводки
```

В `extraction.py` модель извлекает JSON по заданной схеме. Коды нормализуются и сверяются с текстом, названия - со словарём, связи - с допустимыми типами сущностей. Предусмотрена одна повторная попытка; неподтверждённые записи отбрасываются.

В `graph_builder.py` одинаковые сущности объединяются в ориентированный граф NetworkX. Узлы и рёбра сохраняют источники, вес связи равен числу подтверждающих фрагментов. Направление `REPLACED_BY` означает «старая деталь -> новая». Из встречных замен сохраняется более подтверждённая; при равных весах обе удаляются.

В `communities.py` граф делится алгоритмом Лувена с `seed=7`. Для каждого сообщества готовятся компактные записи комплектации, отказов, цепочек замен и признаки полноты. Числа считает Python. За один вызов модель задаёт порядок всех записей; программа сохраняет их значения и проверяет ограничение в 150 слов. Пропуск или повтор номера записи приводит к отклонению сводки. Такой формат сохраняет сведения, которые свободный пересказ мог потерять.

### 2.2. Поиск и агент

Таблица 1 - Четыре режима ответа

| Режим | Как получает ответ | Основное ограничение |
| --- | --- | --- |
| baseline | BGE-M3, четыре ближайших фрагмента, один ответ LLM | Нужный бюллетень или часть статистики могут не попасть в контекст |
| local | Опоры по кодам и словарю, пути графа и цепочки замен | Окрестность не всегда включает все нужные связи |
| global | Map по сводкам, проверяемая аналитика, reduce подтверждённых результатов | Для полного обзора необходимы полные и согласованные записи сводок |
| agent | Выбирает поиск и инструменты ERP, проверяет аргументы и ответ | Возможны неполный план составного запроса и ошибки восстановления |

Local в `search.py` выбирает пути до трёх связей между опорами; при одной опоре использует окрестность до двух связей. Модель указывает номера фактов, подтверждающих ответ. При отсутствии доказательств возвращается отказ.

Global выполняет map по сводкам сообществ, затем reduce объединяет полезные результаты. Для статистики и каталогов `analytics.py` считает суммы, сравнивает модели, прослеживает замены и проверяет полноту выбранной области. Вычисления используют записи сводок; граф служит для проверки этих записей и определения источников. Проверенные строки выводятся без изменения чисел и названий. Для остальных вопросов сохраняется обычное объединение частичных ответов.

В `agent.py` разрешено до шести вызовов инструментов из `tools.py`: поиска, обзора, остатка, цены и заказа. Для первого обзора сохраняется исходный вопрос. Полный проверенный ответ, не требующий ERP или заказа, передаётся пользователю без пересказа.

Цены и остатки берутся из ERP, поставщики - из документов. Цена сверяется с артикулом, остаток - с парой «артикул - склад», количество заказа - с явно указанным количеством пользователя. Неполный или неподтверждённый ответ направляется на исправление. При недоступности ERP предусмотрено до трёх попыток обращения. Подготовка и фактическое создание заказа разделены.

## 4. Где граф помогает и где уступает

Два примера из сравнения четырёх режимов показывают, когда граф помогает найти ответ, а когда выбранного контекста недостаточно.

**Выигрыш: актуальная деталь.** На вопрос «Какую деталь заказать при ошибке E-17 на AR-210?» baseline выдал исходный P-1042: бюллетень SB-2025-03 не попал в контекст. Local проследил связи от ошибки к пусковому реле и от модели через P-1042 к P-1042B. Он вернул действующую деталь и сослался на руководство и бюллетень. Оба режима сделали по одной генерации; local использовал 346 токенов, baseline - 1735. Явная связь помогла найти замену без передачи лишних фрагментов.

**Проигрыш: поставщик после замены.** На вопрос «Кто сейчас поставляет деталь узла “реле давления” для модели GS-520?» baseline нашёл руководство и бюллетень SB-2025-07 и правильно ответил «АвтоматикаСевер». Local отказал: связь поставщика конечной P-3126B не попала в выбранную окрестность. Он потратил две генерации и 2289 токенов, baseline - одну и 1371 токен. Агент нашёл ответ уточняющим запросом. Граф полезен только при достаточной полноте выбранных путей.

## 5. Почему система ошибается

В последней проверке остались пять неправильных ответов. Ошибки возникают при выборе контекста и действий, даже когда нужные сведения уже есть в графе.

**Обратное чтение связи, этап ответа local.** В probe-02 спрашивается код ошибки для SP-113. Ожидался E-23, получен отказ. Связь `E-23 -FIXED_BY-> SP-113` присутствовала в найденных фактах, но поиск не использовал её для ответа в обратном направлении. Причина не в отсутствии исходных данных.

**Направление замены, этап запроса агента.** В probe-05 нужен непосредственный предшественник P-3062C: P-3062B. При пересказе потеряно условие «предыдущая ревизия»; вместо ответа получен отказ. В фактах есть вся цепочка P-3062 -> P-3062B -> P-3062C, но к ней применён неверно сформулированный вопрос.

**Неполный контекст, этап поиска.** В probe-10 требуются замена P-2110 и модели с исходным номером в руководствах. Ожидались P-2110B, BZ-210 и BZ-220. В контекст попала замена, но не входящие связи комплектации моделей, поэтому ответить на вторую часть по переданным фактам было нельзя и система отказала.

**Восстановление и составные действия, этап агента.** В probe-07 после отклонённого поиска агент вернул незаполненный шаблон вместо узла, артикула и регламента. В probe-24 замена P-3062B -> P-3062C найдена, но агент не выполнил запросы цены и остатка. Правильный итог здесь - P-3062C, 33 190 рублей и три штуки в Казани. Найденный факт не всегда превращается в полный план действий.

Влияние размера Qwen 4B отдельно не измерялось: для такого вывода нужно сравнить модели при одинаковых коде, данных и вопросах. Результаты позволяют указать конкретные ошибки обработки, но не приписать их все размеру модели.

## 6. Границы системы и подтверждение человеком

Ассистент консультирует и готовит заказ. Перед фактическим созданием заказа в ERP код проверяет явное подтверждение пользователя. При корректных параметрах вызов без подтверждения возвращает `needs_confirmation=True` и параметры `pending_action`; операция не выполняется.

Например, для E-20 на BZ-120, двух деталей со склада Москва, подготовлено действие `create_service_order` с P-2054C, количеством 2 и моделью BZ-120. В ERP подтверждены остаток 6 и цена 6750 рублей. Создание разрешено только при `confirm=True`; модель не может заменить этот признак фразой «заказ создан». В контрольных прогонах реальные заказы не создавались; путь с подтверждением проверен программными тестами.

Если количество отсутствует, отрицательно или неоднозначно, агент должен запросить уточнение. Он не берёт количество нового заказа из остатка, старой заявки или цифр артикула. Просьба «подготовь заказ» требует настоящего подготовленного действия, а не обещания в тексте. В текущей проверке оба вопроса на подготовку заказа выполнены с нужными параметрами и остановкой перед созданием; это исправляет выявленный ранее пропуск действия.

## 7. Следующий шаг

**Что хотим улучшить.** Следующая идея - точнее отвечать на вопросы, в которых связь нужно прочитать в обратную сторону. Например, по регламенту SP-113 найти код ошибки E-23, по P-3062C назвать непосредственно предыдущую ревизию P-3062B, по исходному артикулу P-2110 определить модели BZ-210 и BZ-220. Все эти сведения уже есть в графе. Поиск умеет обходить связи в обоих направлениях, но нужные факты иногда не попадают в выбранный контекст, а при переформулировке вопроса агент может потерять условие «предыдущая ревизия» или «исходный артикул».

**Как предлагаем это сделать.** Перед поиском нужно явно определять, какая сущность известна и какую требуется найти, и сохранять это условие в запросе агента. При отборе фактов в `local_search()` предлагаем приоритетно сохранять связи, которые подтверждают нужное направление. Для ошибки по регламенту это входящий `FIXED_BY`; для непосредственно предыдущей ревизии - один входящий `REPLACED_BY`; для моделей с исходной деталью - входящие `HAS_PART`. Например, из записи `P-3062B -REPLACED_BY-> P-3062C` следует, что предшественник P-3062C - P-3062B. Правила длины путей и размера окрестности остаются прежними, ответ должен ссылаться на подтверждающие документы.

**Как проверим результат.** До запуска зафиксируем 12 пар прямых и обратных вопросов: по четыре пары на каждый из трёх типов связей, всего 24 вопроса. Для каждой пары подготовим эталоны по исходным документам. Затем сравним текущую и доработанную версии при одинаковых графе, модели и настройках, без кеша ответов. Предлагаемый критерий успеха - как минимум четыре дополнительных правильных ответа на новом наборе без потери ранее правильных ответов на текущих наборах из 24 и 32 вопросов.

**Ожидаемая польза.** Такая доработка должна уменьшить отказы и ответы не на тот вопрос, когда пользователь спрашивает о предшественнике детали или ищет объект по обратной связи. Для неё не требуется менять исходные документы или обучать модель. Это план следующего эксперимента; изменение ещё не реализовано, прирост точности не измерен.
