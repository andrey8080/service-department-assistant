Что делает ассистент

Помогает сервисному инженеру найти нужную деталь по документации, проверить её цену и остаток в учебной ERP, а после подтверждения — создать заказ.

Сначала — подготовка знаний

Документы → фрагменты текста → сущности и связи → граф знаний → сообщества и сводки

Qwen предлагает факты из текстов. Код проверяет их, объединяет в граф и сохраняет базу для дальнейшего поиска.

Исходные руководства, бюллетени, инструкции и отчёты: data/corpus. Подготовкой управляет build_index() в src/assistant/infra/indexing.py.

Затем — ответы на вопросы

Вопрос → поиск фактов → при необходимости ERP → проверка → ответ и источники

Программа загружает сохранённую базу и выбирает способ поиска. Все документы заново при каждом вопросе не обрабатываются.

Вопрос приходит из терминала или HTTP-запроса. Документы подтверждают технические сведения; ERP сообщает цену, складской остаток и результат заказа.

Один вопрос через весь проект

«Ошибка E-17 на AR-210. Какую деталь заказать и есть ли она в Казани?» Поиск находит пусковое реле P-1042 и замену P-1042B. Агент проверяет остаток нужной детали в ERP и составляет ответ. Заказ оформляется только с подтверждением.

Какой режим за что отвечает

baseline Поиск по текстам

Находит похожие по смыслу фрагменты через числовые векторы и передаёт их Qwen. Это обычный RAG для сравнения.

Подходит для сведений из конкретного документа.

local Поиск по связям

Распознаёт коды и названия в вопросе, отбирает связанные факты графа знаний.

Деталь, ошибка, процедура, поставщик, цепочка замен.

global Обзор по сводкам

Собирает частичные ответы по сообществам и объединяет полезные сведения.

Частые отказы, сравнение моделей, перечни по линейке.

agent Поиск и действия

Выбирает поиск и при необходимости вызывает инструменты ERP.

Технический вывод вместе с ценой, складом или заказом.

Режимы local и global сами не обращаются к ERP. Для текущей цены и остатка нужен режим agent.

Проверки

Почему проект устроен так

За каждым разделением кода стоит конкретная задача. Откройте решение: сначала проблема, затем выбранный подход, его польза и ограничения. Указанные функции можно найти через поиск на графе.

Почему подготовка документов отделена от ответа

Задача. Извлечение фактов из всего корпуса требует многих обращений к модели. Повторять его для каждого вопроса долго и дорого.

Решение. build_index() один раз строит граф и сводки, save_kb() сохраняет их, а load_kb() восстанавливает готовую базу. LLMClient отдельно кеширует одинаковые запросы к модели.

Что даёт. При ответе программа тратит время на поиск и нужные действия. При повторной проверке неизменившиеся запросы могут читаться с диска.

Ограничение. Сохранённая база не обновляется сама после правки документов или извлечения: её нужно перестроить. Кеш возвращает прежний ответ лишь на такой же запрос; новый промпт требует нового вычисления. Попадание в кеш не доказывает устойчивость нового запуска модели.

Пример. Команда index читает руководства; затем несколько ask используют полученный graph.json. Изменение текста запроса к Qwen меняет ключ кеша.

Где в коде: src/assistant/infra/indexing.py · build_index(); src/assistant/infra/indexing.py · save_kb(); src/assistant/infra/indexing.py · load_kb(); src/assistant/infra/llm.py · LLMClient._cached().

Зачем строить граф, если уже есть поиск по текстам

Задача. Ответ может лежать в нескольких документах: руководство связывает оборудование с деталью, а бюллетень сообщает её замену. Похожие фрагменты не всегда содержат всю цепочку.

Решение. Граф хранит явные отношения между сущностями. local_search() отбирает связанные факты. Параллельно сохранён baseline: FlatRag.answer() ищет похожие фрагменты по векторам без графа.

Что даёт. Можно проследить путь от ошибки до детали и её замены, сохранив источники. Baseline позволяет измерить, где дополнительная сложность графа помогает, а где обычного RAG достаточно.

Ограничение. Граф содержит только извлечённые отношения. Пропущенная или неверная связь ухудшает ответ; сам факт наличия графа не гарантирует превосходства над baseline. Текстовый поиск иногда лучше сохраняет подробности исходного описания.

Пример. E-17 → пусковое реле; AR-210 → P-1042; P-1042 → P-1042B. Разные связи отвечают на разные части вопроса, а не заменяют друг друга.

Где в коде: src/assistant/graphrag/graph_builder.py · build_graph(); src/assistant/graphrag/search.py · local_search(); src/assistant/infra/flat_rag.py · FlatRag.answer(); src/assistant/infra/evaluation.py · evaluate().

Почему факты модели сначала проверяют и нормализуют

Задача. Модель может перепутать тип, направление замены или написание кода. Без объединения одна деталь из разных документов станет несколькими узлами.

Решение. extract_chunk() проверяет схему, наличие сущностей в тексте и документные ограничения. Нормализация приводит коды к общему виду. build_graph() объединяет узлы и записывает источники отношений.

Что даёт. Поиск проходит через общие сущности, а неподтверждённые записи отбрасываются. Видно, из каких фрагментов взят факт; вес отношения отражает число разных фрагментов-источников.

Ограничение. Вес не является вероятностью истины или числом физических поломок сам по себе. Проверки структуры и текста не распознают любую смысловую ошибку. Отбрасывание сомнительных записей может уменьшить полноту графа.

Пример. Написания p-1042 и P‑1042 сводятся к P-1042. Обратную замену нельзя принять только потому, что оба кода существуют: нужно проверить направление по документу.

Где в коде: src/assistant/graphrag/extraction.py · extract_chunk(); src/assistant/graphrag/extraction.py · _replacement_directions(); src/assistant/infra/grounding.py · normalize_code(); src/assistant/graphrag/graph_builder.py · build_graph().

Зачем нужны сообщества и два способа поиска

Задача. Точный вопрос о P-1042B и обзор «что чаще ломается в линейке» требуют разного охвата. Весь граф слишком велик, а ближайших связей для обзора мало.

Решение. Louvain делит граф на связанные сообщества. Для них готовятся сводки до 150 слов. local_search() работает с конкретными сущностями и их связями; global_search() получает частичные ответы по сводкам и объединяет полезные.

Что даёт. Точечный поиск не передаёт весь корпус, а обзорный охватывает разные части графа. Статистику перед сводкой считает Python; модель выбирает и формулирует сведения.

Ограничение. Сообщество не обязано совпадать с продуктовой линейкой или отдельной моделью оборудования. Сводка сжимает сведения и может что-то опустить; нужны граничные факты и полные итоги. Global требует больше обращений к модели. Local и global сами не получают текущие остатки ERP.

Пример. «На что заменить P-1042?» — local. «Какой узел чаще отказывает у Арктики?» — global с итогами по всей линейке, а не случайным подсчётом в одном сообществе.

Где в коде: src/assistant/graphrag/communities.py · detect_communities(); src/assistant/graphrag/communities.py · summarize_community(); src/assistant/graphrag/search.py · local_search(); src/assistant/graphrag/search.py · global_search().

Почему цену и остаток нельзя брать из ответа модели

Задача. Техническая документация не подтверждает текущую цену, складской остаток или успешное создание заказа. Эти сведения могут меняться независимо от корпуса.

Решение. Агент вызывает check_stock(), get_price() и create_service_order(); Python-клиент обращается к отдельной учебной ERP по HTTP. Поиск в документах и учётные данные остаются разными источниками.

Что даёт. Цена и остаток в ответе опираются на результат сервиса. Нулевой остаток отличается от ошибки сети. Программа может сообщить, какой именно запрос не удался.

Ограничение. ERP может быть недоступна или отклонить запрос. Документная цепочка замен и статус discontinued — разные сведения: текущий статус приходит из ERP, а не из отсутствия или наличия произвольной связи. Ответ отражает данные учебного сервиса на момент запроса.

Пример. Поиск устанавливает нужную деталь P-1042B. Только get_stock(P-1042B, Казань) сообщает остаток в Казани; документ о замене не содержит этого остатка.

Где в коде: src/assistant/agent/tools.py · build_tools(); src/assistant/infra/erp_client.py · ErpClient.get_stock(); src/assistant/infra/erp_client.py · ErpClient.get_price(); erp/app.py · create_app().

Почему модель предлагает действие, а выполняет его Python

Задача. Языковая модель может предложить неизвестный инструмент, перепутать код оборудования с деталью, придумать число или создать заказ без достаточных оснований.

Решение. run_agent() получает предложение модели, проверяет имя и аргументы инструмента и передаёт управление известной Python-функции. Заказ требует подтверждения; итоговый ответ проходит проверки по результатам поиска и ERP.

Что даёт. Вызовы имеют заданный интерфейс, ошибки возвращаются в цикл агента, а действия и их результаты видны в журнале. Отдельно проверяется, что ответ содержит запрошенные сведения и не приписывает ERP неподтверждённые числа.

Ограничение. Проверки покрывают определённые виды ошибок и не гарантируют правильность любого текста. Подтверждение разрешает действие, но не делает неверные аргументы верными; их проверяют отдельно. Лимит шагов и повторы ограничены, поэтому агент может завершиться отказом.

Пример. check_stock(part_id=AR-210) отклоняется: это оборудование, а нужен P-код детали. Предложенный заказ без confirm возвращает запрос подтверждения вместо выполнения.

Где в коде: src/assistant/agent/agent.py · run_agent(); src/assistant/agent/tools.py · validate_arguments(); src/assistant/agent/agent.py · _verified_fields(); src/assistant/agent/verification.py · unsupported_facts().

Как читать карту кода

На экране показано устройство программы. Граф знаний внутри ассистента — другая структура: там связаны оборудование, детали и ошибки.

Три основных представления

Главные вызовы
Какие главные функции связаны между собой. С этой карты удобно начинать знакомство с кодом.
Данные: подготовка
Откуда берутся документы, что получается на этапах обработки и как сохраняется база знаний.
Данные: ответ агента
Как вопрос проходит через поиск и ERP, какие результаты возвращаются агенту.

Нажмите на функцию: справа появится краткая информация, снизу — входные данные, их происхождение, шаги работы, результат и фрагмент исходника. У блоков данных и связей — собственные пояснения.

Если хочется узнать, как функция устроена внутри, нажмите «Развернуть этот участок графа». Подробная схема показывает её помощников и связанные вызовы. Все такие схемы подряд читать не требуется.

Рамки подсистем объединяют функции по ответственности: извлечение, граф знаний, поиск, агент и другие части. Это границы задач, а не очередность выполнения. В одном файле могут быть функции разных подсистем: например, cli.py содержит и запуск команды, и получение готовой базы. Клиент ERP работает внутри ассистента; учебная ERP — отдельный процесс, с которым клиент общается по HTTP.

Блоки и стрелки

Карточка функции

Имя, краткое действие и файл реализации. Например, LLMClient.chat() — метод; путь к Python-файлу указан отдельно.

Сплошная стрелка на схеме вызовов

Функция у начала стрелки вызывает функцию у её конца. На схемах данных такая стрелка показывает передачу данных.

Пунктир — другой вид перехода

Выбранный обработчик, проверка значения, свойство или HTTP-запрос. Конкретный вид указан в подписи.

Блок на стрелке — данные вызова

Передаваемые аргументы и результат. Нажмите, чтобы увидеть строку вызова и откуда пришли значения. Это пояснение связи, а не дополнительная функция.

Зелёный блок — данные

Документ или промежуточная структура. На схемах данных стрелки показывают передачу и преобразование результатов.

Карта показывает возможные связи, а не запись запуска. Ветвь выполняется при своих условиях, а цикл может повторить вызов. Возвращаемое значение описано в подписи, отдельной стрелки назад нет. Нажатие на блок только открывает пояснение.

Пример чтения: part_id — имя параметра, "P-1042B" — переданный аргумент. В разборе показаны настоящие строки исходника; пропущенные строки отмечены. Значения из примеров не являются измерениями конкретного прогона.

Управление просмотрщиком

Выбрать и найти

  • Нажмите на блок или связь. Остальные участки приглушатся, чтобы легче проследить ближайшие связи.
  • Снять выделение: кнопка «Снять выделение» или щелчок по пустому месту. Приглушённые блоки тоже можно выбирать.
  • Поиск в шапке находит функцию по имени, файлу и назначению. Выберите результат, чтобы открыть её на схеме.

Перемещаться и менять масштаб

  • Перетаскивание двигает граф; колёсико и кнопки − / + меняют его масштаб. На сенсорном экране — два пальца.
  • «Вся схема» помещает граф целиком в поле просмотра; «100%» возвращает обычный масштаб. Двойное нажатие на блок центрирует его в 100%.
  • Мини-карта показывает всю схему и видимую область. Нажмите на нужное место, чтобы переместиться туда.

Термины и материалы

Термины собраны по темам. Откройте нужную строку, чтобы прочитать объяснение с примерами из проекта.

Код и данные

Функция, метод и класс

Функция — именованный участок кода с входом и результатом. Метод — функция объекта определённого класса. Класс описывает устройство таких объектов. Например, LLMClient — класс клиента, а chat() — его метод.

Аргумент и параметр

Параметр — имя входа в определении функции, например question. Аргумент — конкретное переданное значение: «Что заказать при E-17 на AR-210?». В подробном разборе выбранной функции для каждого входа указаны смысл и источник.

Возврат, None и побочный эффект

return отдаёт значение вызывающему коду. None означает отсутствие полезного возвращаемого значения. Функция при этом может записать файл, изменить объект или напечатать ответ — это отдельный результат её действия.

str, int, bool, list, dict и set

Это формы данных Python: str — текст, int — целое число, bool — True/False, list — упорядоченный список, dict — словарь «ключ → значение», set — набор без повторов. Запись list[Chunk] означает список фрагментов, а не новую функцию.

Модуль, self и вложенная функция

Модуль обычно соответствует Python-файлу. self — текущий объект, который Python передаёт методу автоматически. Вложенная функция может помнить переменные внешней функции: это замыкание. Поэтому не все используемые данные видны в её списке аргументов.

Обработчик, callback и lambda

Функцию можно передать как значение и вызвать позже. Например, runner() выбирает обработчик вопроса. Lambda — короткая запись функции. Создать обработчик и выполнить его — разные действия.

Документы и граф

Граф вызовов и граф знаний

На схеме вызовов вершины — функции; на схемах данных есть также документы и промежуточные структуры. Внутри приложения граф знаний устроен иначе: его вершины — оборудование, детали, ошибки и другие сущности, а связи — факты из документов.

Модель оборудования и языковая модель

Model в данных — модель оборудования, например AR-210. Qwen — языковая модель, которая читает текст и формирует ответы. Это два разных значения слова «модель».

Физический узел, деталь и вершина графа

Component «пусковое реле» — вид физического узла. Part P-1042 — конкретный артикул детали. Вершина графа — запись о любом объекте: это может быть Component, Part, Model или код ошибки. Слово «узел» без контекста легко спутать.

Фрагмент, сущность и отношение

Chunk — часть исходного документа. Entity — распознанный объект с именем и типом. Relation — направленный факт о двух объектах: например, AR-210 HAS_PART P-1042. Объект и утверждение о нём — разные вещи.

Источник и вес связи

manual_AR-210.md#0 означает первый фрагмент руководства, а не строку файла. У связи хранятся подтверждающие фрагменты. Вес — их число; повтор одной записи в том же фрагменте вес не увеличивает. Это не статистическая уверенность.

Модели и поиск

LLM, токен и контекст

LLM — языковая модель. Токен — единица текста для модели, примерно кусок слова. Контекст — сообщения и факты, переданные в текущем запросе. Большой корпус не означает, что модель получает его целиком при каждом вопросе.

Эмбеддинг и baseline

Эмбеддинг — числовой вектор текста: похожие по смыслу тексты стараются расположить рядом. Baseline использует близость векторов, а local и global — граф знаний и его сводки. Векторы создаёт bge-m3.

Сообщество, map и reduce

Сообщество — группа связанных вершин графа знаний. Map получает частичный ответ по каждой сводке, reduce объединяет полезные части. Это организация поиска; задачи не обязательно исполняются параллельно.

Индекс и кеш — в чём разница

Индекс — подготовленная база знаний: граф и сводки, по которым мы ищем. Кеш — сохранённые ответы модели на конкретные запросы. Изменение алгоритма поиска не всегда требует извлекать документы заново; изменение правил извлечения может потребовать пересборки индекса.

Кеш и воспроизводимость

Кеш сохраняет ответ сервиса для точного запроса. Повтор может обойтись без вычислений модели. Такой повтор проверяет обработку сохранённого ответа, но не доказывает устойчивость нового ответа модели без кеша.

Сервисы и проверка

API, HTTP и ERP

API — согласованный способ обратиться к другой программе. HTTP переносит запрос и ответ между процессами. Учебная ERP хранит цены, остатки и заказы. Ollama предоставляет отдельный API языковой модели.

JSON, схема и валидация

JSON — текстовая запись словарей и списков. Схема описывает ожидаемые поля и типы. Валидация отсеивает неправильную структуру или значения, но сама по себе не доказывает смысловую истинность ответа.

Ошибка, исключение и отказ

Исключение — сигнал кода о проблеме, например недоступной ERP. Отказ refused означает, что поиск не нашёл достаточно оснований для ответа; программа при этом может работать штатно. Нулевой остаток qty=0 — известный результат, а не ошибка соединения.

Точность, полнота и тесты

Precision показывает долю верных извлечённых фактов, Recall — долю найденных эталонных фактов. Доля решённых вопросов оценивает ответы. Модульные тесты проверяют код на заданных сценариях; это не та же метрика.
